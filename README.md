I want to make a lightweight me-specific playtesting tool for a board game I'm making. the board game requires: ~120 hexagonal tiles (95 x 83 x 0.3 mm), ~120 mini size game cards (41mm x 63mm), ~120 8mm cubes in a variety of colors, and 6 meeples. the tool should allow me to write typscript to define components in an object oriented manner, with inheritence. so to create my 120 hexagonal cards (assuming 60 are type A and 60 are type B, all the same size), I might create a type A inheriting from the base hexagonal type (which defines my standard dimensions), which in turn inherits from the Card type, whose only invariants are that it defines a valid 2D shape and that it implements front and a back image properties, whose return value's dimensions match the cards' dimensions. the user could define arbitarily complex behavior for composing their game pieces into classes, as long as they implement the dimensions and image properties. the system would also expose base classes for 3-dimensional objects (return a bounded 3 dimensional shape + a single color (no texturing in v1)).

the system should treat 2D images as first class citizens, with their own base class (Image) (Card.FrontImage must be an instance of an Image), which are 2D bitmaps. Images can be composed onto eachother; you could create an Image A as a typescript object, then create image B, then paint Image A onto image B at coordinates X,Y (layering determined by paint order, with later paints winning). Image aspect ratios most match the Card they are applied to. Image dimensions should match the shape of the Card they are filling. the system should offer some utilities for creating simple bitmaps (single color, text), but most image generation and manipulation will be done outside of this program.

the system would render these definitions onto a flat isometric plane and implement a physics engine for manipulating them (no need to model Z axis (up/down) outside of a simple stacking system; by default, pieces are on the playing surface (z-index: 0). if moved "over" another piece, the move on top of that piece (z-index += 1). moving a piece moves that piece and everything above it (check all coordinates above that piece; if any other piece occupies that same coordinate at all and has a higher z-index, move that piece along with the original piece. once placed, reset all z-indexes to the base piece's index, then increment up the stack. moving pieces have a z-index = the highest z-index on the board + 1, so that they cannot collide with a tower of pieces). 3d pieces are implemented with a simple bounding cube). no need to model collisions (pieces can only be moved explicitly by the player, and always slide on top of each other when overlapping).

Cards which occupy any of the same space (even a partial overlap) should stack on top of eachother based on the order they arrived. order should be obvious from movement: a card exists, another card is moved on top of it, that card is on top. when actions are applied to stacked objects, they should only apply to the top object. if objects partially overlap and a lower object is selected, all objects on top of it should move as well. actions like flipping and rotating can apply to any selectable object within a stack and should only be applied to that object (not objects above it)

the system explicitly does not support gameplay scripting/logic; it's simply a piece simulator.

the system would also offer a board layout phase as part of the typescript program; defining the size of the playing space and where each piece starts on it. pieces in scope in the program are identified by a globally unique id/handle, and all exist in a ghost space which is not rendered by the engine. pieces are rendered when the script makes an initial "ghost -> coordinates" move.

the system should also offer the user the ability to flip and rotate (double click to flip, any number of degrees by holding the right click button + dragging, double right click to rotate 45 degrees, behavior overwritable as part of the class system) Cards and Objects.

the system should allow the user to pan around the table, rotate their POV around the current focal point, and zoom in and out.

the system translates between pixels (images, screen rendering) and dimensions (defined in metric) at a 10 pixel per mm ratio, and keeps them consistent when zooming in/out + rotating POV.

Cards should have a small height (.3 mm), which isn't configurable by the player (simply for isometric satisfaction)

the system's workflow should be: write and modify the typescript board definition file; run that file, which generates a completed board object with card and object entities, each with its coordinates and z-index. then, start a web server, which serves a website rendering the board and applies any player-input to the board. for now, we can assume localhost-only + a single user.

v0 does not need to implement multi-user UI manipulation, but a later version probably will.
